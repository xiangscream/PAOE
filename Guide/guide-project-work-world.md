## 操作与参考
<!-- paoe:reading-header:end -->

**库应当越用越清楚：成果回到主题，过程及时退出，读者能顺着联系找到足够的信息。** 保持干净是每项任务的收尾责任，也包括新增和修改文件时的日常选择。

## 一、先有阅读架构，再决定文件去向

每个库用已有首页说明用途、当前主线和少量主题入口。按读者的问题组织，沿“入口 → 主题 → 具体成果、做法与依据”逐步展开；主题之间连接真实的前提、应用、取舍和借鉴关系。目录负责存放，正文负责解释关系。

内容少就在同一页展开，具有独立用途的长内容才拆页。HOME、INDEX、README各自承担明确职责；只复述另一页或列同目录文件的空壳合并删除。无需为每个目录建说明页，也不按聊天、批次、设备或交付次数永久拆出一套架构。

搜索命中的深层页也应让人知道它解决什么、属于哪个主题，以及内容的适用时间或状态。已有原件可以直接进入；需要补背景时有路可循。

## 二、每份文件留下来，都要有具体用途

判断一份文件时问：**拿掉它，会丢掉什么正在使用或值得以后使用的内容？** 按内容和实际依赖判断，文件名、年代、发言者和“来源”身份都不是自动保留理由。

| 判断 | 处理 |
| --- | --- |
| 整篇仍有独立用途 | 保留，删重复和过时口径，接入相关主题或操作入口 |
| 只有部分有价值 | 将独有内容并入已有正文或Tips，保留必要语境与来源，再移除旧载体 |
| 没有独有价值，也无当前依赖 | 删除；普通回执、重复草稿和可重建临时物不默认归档 |
| 独有原件确需追溯，但不再用于日常阅读 | 移到库外历史，相关正文保留准确出处 |
| 仍有未完责任、待审决定或运行依赖 | 保留并接入对应TODO与业务入口，只处理受影响的具体部分 |

有价值的失败和过时取舍可以留在正文：它们解释后来为什么改变。单纯催办、转交、重复确认通常没有长期价值；夹带的新意图或判断只提取有用部分。零散想法可以暂存Tips，不强行分类，也不因尚未成熟而丢弃。

## 三、同一事实只维护一处

现行业务口径、职责、方法、机器事实分别回原维护位置，其他页面引用。项目库保留业务成果与必要依据，System维护运行规则与配置入口，Libraries维护通用方法，EXM保存值得跨任务记住的原始意图、个人经历、业务取舍和有用联系。

EXM作为全局外置记忆，可在过程中吸收有长期价值的经历和心得，不必等待项目验收或收口。经历中的阶段状态按发生时表述，当前业务决定仍回原项目。

优先更新已有正文。确需新文件时，创建者同时明确其用途和归属，并从相关正文或入口连接过去。已有权威原件用链接，避免为了入库、交接或图谱再造副本。原始材料、Human批注和已审版本按其实际用途保护，来源归属清楚。独有Human原话先完整归位并保留说话人、语境与来源，再清理旧载体；摘要不替代唯一原话。

## 四、联系要让读者多懂一件事

在相关句子里说明为什么值得继续读：前后转折、结论依据、实现依赖、跨项目借鉴、反复出现的教训，都是有效联系。库内链接优先指向具体正文或标题；跨库链接回权威原件。

孤点是待判断线索。先判价值，再决定合并、退出或补真实联系。长期正文应能从适当入口到达，必要运行文件从操作入口可达，未完输入从对应TODO可达。允许暂未成形的想法；不要机械挂总目录、相互乱链或复制跨库正文来凑连线。

图谱帮助发现内容脱节和层次失衡。全库清理结果要在显示孤立文件、没有隐藏待清理范围的视图下检查；专题筛选可以用于阅读，但不能充当全库清理结果。还要检查从首页向前能否读到主要正文，不能只看有没有连线。

## 日常顺手维护

创建或采用材料时就接入所属主题或操作入口，明确用途和维护者；临时材料关联本项Task。后续在实读成果回告、阶段交付、独立TODO或本工作结束时，由实际执行者当场归位和清理；整体工作沿原负责人汇总，复用已有成果：

1. 成果写回对应主题，更新当前入口和本人TODO；有长期新增时将必要原话、纠偏与结果交EXM整理者。
2. **普通交接阅后即焚**：实读、办结且无未完依赖后，处理本项Mail、Notice、临时note/message、旧候选、写入载荷和中间文件。内容归位后沿正式[输入收尾](input-cleanup.md)入口删除通信及关联侧记录，不默认归档。发件人实读成果回告后也处理自己收到的回信和通知；双方各清本人收件，不代造他人消费。
3. 未完输入继续关联实际责任，写清下一动作或等待。撤回、替代与实际消费按真实事实办理，不替别人补造“已读”。
4. 移动或合并时同步转接当前阅读引用；必要出处转到库外原件。移除真正被调用的路径前，接好具体调用者。

已交清阶段先把后续责任与来源接到真实业务正文，再清已办载体；大Task继续存在不延长所有阶段过程件的寿命。确需保留的待审、未完和运行材料各有实际入口。

短期运行文件可以存在，其使命结束后就应退出。完成任务时只接收回报、留下回信与通知等待别人再清，是收尾遗漏。夜间维护只补漏，不用每天全库重扫代替随手归位。

## 六、清历史积压，用整组裁定和批量执行

先给整理者一份简短库总览：用途、主题网络、已有承接内容和当前依赖。随后按日期、完整工作组或资料包交待清理全文。非主题过程件原则上每批上百份；例如同组有210份Works，就整体交付，不再人为拆成数十轮。输入规模以能完整读取和判断为限，超过承载能力时按完整子组拆分并说明覆盖范围。

明确已结束的普通回执成组清理；内容混杂的才做语义筛选。已经裁定、吸收的内容直接复用，只复核新增冲突。材料不足时保留具体例外，其他已明确部分继续。

每组只交必要去向：保留项及理由、提炼正文及目标、删除或库外归档范围、未决例外。大组同判可以给范围和例外，不必为每份文件写报告。原始包迁出和其中独有内容已完成筛选是两件事，未筛范围接入已有任务即可。

内容判断期间，本地执行者可处理上一组已放行的目录、链接和运行收尾。复用侧边Chat已经交付且在本批授权内的裁定，执行者核必要的人工改动、本地依赖、来源和新冲突，不重新全量审一遍。全文、向量及旧路径退出合批交检索维护者，已有明确回告直接采用。

## 七、清理过程本身也要收敛

有效经验回现行指南，实际进度回原TODO，去向映射按需要留一组。不要为每封回信、每次删除、每次索引刷新再建一份正文、审阅报告或总结；已有结果能说明的事直接链接。普通回执也不搬到另一座永久历史库。

批量删除或合并独有材料前，按原路径留一组可恢复底稿，复用已有保全原件。只对不确定且有实际影响的例外补证，不无需求增加多重备份、哈希和重复核验。正式通信使用系统入口，配置、身份、代码和运行依赖按原维护边界处理；报错明确停住受影响操作，报告实际完成部分。

## 八、用真实阅读和退出结果判断完成

清理后检查三件事：

- **读得懂、找得到：** 从首页走两三条真实问题路线，逐跳能获得足够信息；深层页也能补足主题背景。关系要讲得通。
- **旧负担确实退出：** 清理范围中的过期过程件不再占日常库；剩余项各有用途和真实责任。孤点、断链与不可达项按内容判断处理，不靠筛选遮住。
- **原件和工作接得上：** 独有原话、人工批注、必要历史及未完输入可追；受影响链接与运行入口接续，检索维护范围交清。

报告实际处理范围、保留理由和未完例外即可。文件减少量、批次数、零孤点和索引刷新各有用途，都不能单独代表库已经好用。发生新摩擦，直接改对应规则和下一次做法。

## 九、项目文件和当前入口

各库沿已有职责应用上述规则，不机械复制同一目录。项目沿现行约定放置：

| 内容类别 | 规范位置 | 说明 |
| --- | --- | --- |
| 当前业务正文、分析、复核与报告 | `Works/` | 复用已有业务主题；稳定成果更新原正文并接入 INDEX，不强制全部移入 Decisions |
| 正式决策、被接受的结论与基线 | `Decisions/` | 项目形成的权威决议与正式方案 |
| 原始录音、下载、截图、外部附件快照 | `Materials/` | 保留原文件名与必要来源；项目经验默认归 `Materials/TIPS.md` |
| 尚未确认归属的临时输入 | `Inbox/` | 待分类材料暂存处；由 Coordinator 明确去向 |
| 外部 live 飞书、共享源码与云端文档 | `INDEX.md` 或成果正文中的稳定链接 | 保持云端权威，不造本地冒充副本 |
| 本人 ENTRY、TODO、Mail、私有笔记 | `Workstations/<Sxxx>/` | 各自独立工位；TODO 仅维护当前未完责任 |
| 确需追溯的独有过程材料、旧版本快照 | 库外历史目录（如 `<项目>-History`） | 活跃 Vault 内仅留简短索引，避免膨胀 Obsidian 索引 |

项目INDEX维护最新业务口径与成果入口，TEAM维护长期岗位，HISTORY按主题简记阶段变化并链接成果。它们各司其职，不重复整篇正文。无法确认哪份结论生效时，由Coordinator裁决。

项目经验默认进入 `Materials/TIPS.md`，记录场景、做法、依据与适用范围；可用 `paos project experience <项目ID>` 读取。成熟通用方法再提炼进Libraries。必要历史放活跃Vault之外，不以软链接重新挂回；当前正文只留需要的出处。

## 十、文本版本与规则联动

已登记项目的正文、INDEX、TEAM、工位 ENTRY/TODO 与项目约定可纳入项目本地 Git 仓库。

- **排除范围**：排除 `private-data`、运行配置、Token、缓存、大体积媒体和原生会话目录。
- **提交粒度**：只提交自己负责的成果与路径，不使用盲目的 `git add .` 带走同事修改。提交信息写清实际改动。
- **差异与合并**：跨 Windows/WSL 编辑时注意换行符（CRLF/LF），避免整文件虚假 diff。冲突时查看双方新内容再行合并，禁止直接用己方版本整文件覆盖。

每项规则只在一处维护正文。接口改变时同步更新引用它的ENTRY、模板和示例，并实际调用验证；公共AGENTS与PROJECTS等派生内容沿现有生成或同步机制更新，保留人工区。专题修改直接回对应Guide，其他入口保留用途与链接。

升级或迁移时一次接好有效内容和使用方，验通正常读写，再撤旧入口；独有历史按前述价值规则归位。
