# 跨机采用、经历与团队快照

两台电脑分别运行自己的 PAOE，使用 GitHub 更新公共系统和专业方法，通过 Syncthing 共享个人经历及团队背景。每机的同步维护 Agent 接收跨机请求，再沿该机现有原生入口联系真正的目标。

## 内容放在哪里

| 内容 | 正常同步入口 | 维护者 |
| --- | --- | --- |
| System：Core、Guide、公共规则与项目母版 | [PAOE 仓库与固定发行](https://github.com/xiangscream/PAOE/releases) | 系统维护者发布；各机 Rooter 采用 |
| Workflow、Skill、Tool 正文与配套资料 | [PAOE-Libraries 私有仓库](https://github.com/xiangscream/PAOE-Libraries) | 方法维护者发布；各机登记独立库 |
| 每日经历、主题、带日期的项目摘要、TEAM 快照 | 两端已确认的 Syncthing 内容目录 | 各机同步维护 Agent 与原内容 Owner |
| 本机安装位置、Registry、工位与原生连接 | 本机安装和对应 Home | 本机 Rooter、Coordinator 和本人 |

System 与 Libraries 分别采用明确版本。另一台电脑保留自己的数据根、项目与员工身份，按[升级采用](guide-upgrade-adoption.md)更新 System；Libraries 沿其 README 更新正文并重建本机 Catalog。GitHub 变更已发布、各机已采用、业务已实际使用分别记录。

## 经历库与 TEAM

优先复用两机现有共享目录，内容根的相对位置由两端确认。库中保留一个首页，链接日期经历、主题、项目快照、机器责任及团队页。正文应让没有来源项目目录的另一台电脑也能读懂本人做了什么、项目到了哪一步、接下来联系谁。整理方法从已登记的 Libraries 检索“经历库”或“日常输入整理”。

两端都可先保存本机的新经历和来源；需要统一日期成稿时由明确的合成人去重整合。合成职责不成为新增记录的前置条件。

各机将真实项目的 `TEAM.md` 复制为快照，按机器和 Project 分组，例如 `Teams/<machine>/<project>/TEAM.md`。附短来源页，记录来源机器、Project、原件定位、采集时间和维护 Owner；源 TEAM 变化时由该机同步维护者刷新快照和导航。

快照保留同事、岗位与职责的来源口径。来源机的相对工位链接仍属于来源项目；跨机联系通过机器责任页定位同步维护者，由其在本机找实际 Home 和 Contact。快照不表示实时在线，也不作为本机 Registry 或原生绑定。

## 跨机联系怎样接续

```text
发送方 Agent
  → 本机同步维护 Agent
  → 既有共享请求目录
  → 对端同步维护 Agent / 本机接收入口
  → 对端目标的原生提醒
  → 目标实际处理与回告
```

目标使用“机器 + Project + Home”定位。两机可能有相同的项目号或员工号，不能只凭裸编号路由。安装级角色沿本机角色入口联系。

已有文件桥时沿原请求和回执合同工作。请求交具体问题、原件和期望回复；接收端用自己的配置与原生入口执行。经历正文和 TEAM 快照只是背景，具体行动来自明确的协作请求。

文件到达、原生提醒受理、目标实际读到并处理，是三段不同证据。结果未知时查询原请求和原件，保留下一责任与恢复条件；不把重复投递当作恢复。对端离线时保存输入和正常启动入口，由该机本人恢复。

## 另一台电脑的首次采用

1. 从正式 Release 采用固定 System，按该机实际位置保留或登记 Project、Rooter 与 Libraries；原生会话、模型和 STOP 沿本机现有设置。
2. 采用独立 Libraries 的已发布正文，使用同版 CLI 登记库根并重建 Catalog。
3. 在已配对的 Syncthing 目录使用同一相对内容根；本机首页、TEAM 快照和机器责任页引用真实原件。原音、大型项目资料按业务需要单独安排。
4. 两端各自确认同步维护 Owner、合法目标和本机原生入口，再选一次真实协作，核文件到达、原生处理和回告。已完成的步骤直接复用证据。

本机配置、Contact、接收器和运行中的工位状态由各机维护，不从对端快照覆盖。同步通道在线与对端 Agent 当前可接续分别核对。
