# 项目 <project-id> · Work 临时负责人指南

<!-- paoe:common:start -->
## 何时载入本指南

仅当你被指定为某项 Work 的临时负责人（或收到 Human 以 `0` 开头的真实新输入准备组织团队规划）时，通过任务 `source_refs` 或 `paos context read <本人Sxxx> --source WORK-LEAD.md` 完整读取本文。普通成员日常只读 `AGENTS.md`，不每轮加载本指南。

Work 仍是软流程概念，不建注册库、编号或状态机；状态留在业务原件、唯一个人 `TODO.md` 与对应 CAT 房间中。

本指南的公共正文由System母版自动同步，项目补充留在公共区外。负责人在承担新工作或阶段恢复时重读本项目的实际文件；文件同步不代替会话中的重新读取。

## 1. 开工前对齐工作法（先落到底层，再出计划）

不要停在抽象原则或反复问 Human “同不同意”，开工前把目标与原则对齐到四件具体事实，能清楚说出“**触发什么 → 谁做什么 → 看到什么成果**”后再提交团队计划：

1. **先弄清问题与底层原因**：找准真实使用中的断点，判断问题出在资料、界面、合同还是实现。
2. **落清四要素**：① 实际使用行为与触发条件；② 唯一数据来源、成果所属主题入口及维护者；③ 成员分工与协作方式；④ 可观察的结束与验收条件。
3. **用普通路径和会改变方案的反例澄清歧义**：专门挑出“不同理解会导致完全不同做法”的边界问清。
4. **验收看同一条真实使用链**：单元测试、代码合并或版本发布都不能替代真实会话、真机界面与实际采用验证。

### 两个短例

- **例 1（前端直接映射后台）**：不能只口头认同“薄前端”，而要落清——唯一可写事实源是个人 `TODO.md`；前端只读映射后端 `todo.groups` 与角色卡 `group`，不在前端另存可写 TODO 或批准副本；角色卡编辑走同一正式写回入口。
- **例 2（输入 `0` 先组织计划）**：不能只写“支持 0 类规划”，而要落清——Human 在项目会话发出 `0` 开头真实新输入（非引用/历史）→ 接单者立即识别并载入 `WORK-LEAD.md`、先拟团队计划而不直接开工 → Human 看到清晰的团队计划与两次不同内容放行，并在对话或可选界面一次表态生效，不重复弹窗。

## 2. 组织启动与两次不同放行

- **组织 Work 即关联 CAT**：只要是已组织开展的 Work 就必须建并关联专用 CAT（不再等 4 人）；普通零散任务仍直接进个人 `TODO.md`，不因此变成 Work。
- **0 类四步流程**：① 在本人 TODO 登记规划并给出团队计划（`team-plan propose`）→ ② **Human 第一次放行**（`open-plan`）后建专用 CAT 并邀请成员 → ③ 成员在房内完善临时角色卡（`team-plan role`，放行前仅存房间/计划原件，不提前写入正式执行 Task）→ ④ **Human 第二次放行**（`approve-roles`）后由成员接入正式执行 Task（`team-plan enroll`，在现有 `source_refs` 标 `work-group:<工作名>` 与 `cat-role:<room>`）并全员开工。
- **一次决定生效（F87）**：`open-plan`、`approve-roles`、`save-role`、`accept-goal`、`close-room` 均只需 Human 在原对话或可选界面明确表态一次，经 `team-plan review` / `confirm --decision` 直接记录并应用，不再叠加本机弹窗（参数合同见 System OPS 操作指南）。两次放行与最终验收各自独立，未作决定不得伪造，改版不可沿用旧批准。Hook 信任与系统权限弹窗不属 PAOE 业务节点。

## 3. 过程汇集与成员离席

需要稍后回看或依赖同事交付再行动时，把准确时间／交付条件和来源留在相关成员本人的现有Task，由该成员登记铸币检查点；负责人不另建一份接续台账。普通即时工作按原计划连续推进，安排变更或暂停时同步调整相应检查点。完整操作从本人ENTRY所链的System Guide进入《铸币程序：显式检查点接续》（`Guide/mint-checkpoints.md`）。整体述职与Human验收仍按本指南。

- **CAT 汇集本工作 Human 介入**：成员若在与 Human 直接对话中收到本工作介入，由本人判断范围后将相关原话、谁说的、何时及属于本工作哪部分带回本房 CAT（房内已有 Human 发言不重复转帖，Agent 转述不伪装 Human；不做全会话采集或程序审查门）。
- **分阶段退出不扰人**：成员交清本段成果、经历与未完交接即可 `left` 离席（区分暂时 `offline` 与完成本段 `left`）。早期调研等已顺利交付且无待答问题者，不为收尾再唤醒写稿或点离席；必要时由负责人依据已交付事实更新席位。退出房间不丢失成果、原身份或后续再邀请的能力。
- **范围变化控制**：放行后 Human 在房内保存纠正直接生效并提醒对应成员；成员在原授权内连续推进，仅实质改动目标、参与人、职责或交付范围时交受影响差异。

## 4. 负责人单稿述职、验收与关房

1. **统一形成一份本工作意图稿/述职**：临时负责人沿本房 CAT 汇集的 Human 介入原话、已有业务原件与成果，统一整理成一份本工作意图稿与成果述职（不要求各成员按会话逐份交意图稿；已写成员稿作为经历保留）。
2. **Human 明确通过后收口**：将单稿述职交 Human 审阅；Human 在对话或可选界面明确通过（`accept-goal` 直接记录、不重复弹窗）后，再结束整体任务并关闭对应专用 CAT（待审期间保留进展来源，不提前记成已验收）。
3. **完成Work时交回EXM**：将本工作统一意图稿、已交成果及有长期价值的经历来源交EXM当前整理者，作为TODO中本Work完成时的收尾动作；各成员不再另写一轮经历稿。独立TODO按AGENTS由执行者收尾回流。日期视图和业务日结需要时复用这些原件，S053不再每日联动召集供稿。Human的零散想法与主题哲学沿EXM“心得”收纳，原话和Agent理解分开。
4. **每阶段收材料，最终验收后清本项**：核成员成果已进入约定主题、必要原话和未完责任已接住；已交清阶段的普通输入和临时过程件随阶段退出。负责人读完成果回告后同步清本人回信和Notice，复用原述职与TODO，不再增收件证明或清理报告。待Human验收的原件继续保留；最终通过后沿AGENTS与System输入收尾指南处理剩余已办载体。详细归属与阅读网络沿System《库组织、项目文件与 Git》。
